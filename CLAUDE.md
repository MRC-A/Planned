# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Planned is a task and project management app. Multiple views (Table, To-Do, Calendar, Gantt) share the same underlying task data, and a chat panel talks to a locally-run LLM (LM Studio or Ollama, OpenAI-compatible API) that creates and schedules tasks.

**Convention: this repository is English-only.** All code, identifiers, comments, UI text, and documentation must be written in English, even though the maintainer and Claude converse in French. Only chat responses to the user should be in French when the user writes in French.

## Architecture

Monorepo with two independent projects:

- `backend/` — FastAPI + SQLModel/SQLite (Python), package `planned` under `backend/src/planned/`.
- `frontend/` — React + TypeScript + Tailwind v4 + shadcn/ui (Vite), under `frontend/src/`.

The frontend is wired to the backend over HTTP (see below) — there is no more mock data.

### Shared data model

`backend/src/planned/models.py::Task` is the single source of truth for what a task is (title, status, priority, start/due dates, duration, dependency, parent, tags, timestamps). `frontend/src/types/task.ts` mirrors it by hand (camelCase, `tags` as `string[]`) — when a field is added/renamed on one side, update the other, `frontend/src/lib/api.ts`'s `fromApi`/`toApiPayload` converters, and (for a new column on an existing table) `db.py::_COLUMN_MIGRATIONS`, since `create_all()` only creates missing tables, not missing columns. Every view reads from this same shape:

- **Subtasks**: `parent_id`/`parentId` — one level, self-referential (a task with `depends_on` set is unrelated: dependency vs. hierarchy are two separate relationships, both nullable FKs to `task.id`). No separate "subtask" type/model — a task *is* a subtask purely by having a non-null `parent_id`; the one-level-deep rule is enforced by restricting what can be *picked* as a parent, not by the schema. **A task that already has a parent can never itself be picked as a parent, and a task that already has children can't be given a parent either** — both directions enforced in both layers: `TaskFormDialog`'s "Parent task" picker only lists tasks with `parentId === null` as candidates, and hides the picker entirely (with an explanation) when the task being edited already has children; `api/tasks.py::_validate_parent` rejects both directions server-side (400) as defense in depth, plus rejects a task being set as its own parent. (Two bugs found this way, both fixed: an earlier version only excluded direct children client-side, letting a subtask-of-a-subtask be created — invisible in Table, since only one level is ever rendered; a later version validated the chosen parent but not the task being edited, so PATCHing a task that already had children to give it a parent silently formed a 3-level chain. If you ever find another one, `parent_id IS NOT NULL AND parent_id IN (SELECT id FROM task WHERE parent_id IS NOT NULL)` finds it.) Visibility rule, deliberately different from `dependsOn`: a subtask is hidden **everywhere except** (a) Table, once its parent row is expanded, and (b) To-Do, where it's just a normal flat list item — the "toggle" only exists in Table. Calendar filters to `parentId === null` and never shows subtasks at all, even with dates; the Timeline (Gantt tab) deliberately *does* show them, indented under their parent — see its bullet below for why. **Deleting a task never leaves a dangling reference**: `DELETE /api/tasks/{id}` promotes any children to top-level (`parent_id = NULL`, not cascade-deleted — losing the parent shouldn't lose the subtask's own data) and clears `depends_on` on anything that pointed at the deleted task. (Found via a real orphaned row: a deleted parent left a subtask with a `parent_id` pointing at nothing, invisible everywhere but To-Do. If you ever need to fix one by hand, `PATCH` its `parent_id` to `null`.) Covered by `backend/tests/test_tasks.py` (alongside `test_db.py` for the migration path and `test_chat.py` for the chat tool-call sanitizers — the backend suite; the frontend still has no test runner, which is C14/F13's job).
- **Table** (`frontend/src/views/TableView.tsx`) — the main view: one row per task, every field exposed. This is the exhaustive view; other views only surface a subset. Create and edit both go through `components/task-form-dialog.tsx` (same form; `task` prop present = edit mode, pre-filled and `PATCH`-ing via `onEdit`; absent = create mode, `POST`-ing via `onCreate`). Also: cycling status by clicking the status badge, deleting a row (behind a confirmation, see below), expanding a parent row (chevron, `expanded: Set<number>` state) to reveal its subtasks indented directly below.
  - **Delete confirmation & bulk select**: a click on the trash icon no longer deletes immediately — it opens `components/delete-confirm-dialog.tsx` (`deleteTargets: Task[]`/`deleting` state in `TableView`; a plain array rather than a single task so the same dialog serves both the per-row trash icon, `[task]`, and bulk delete below), which says the deletion can't be undone and, if any target task has a child *outside the selection*, how many and that they'll be promoted to top-level rather than deleted too (matching `delete_task`/`bulk_delete_tasks`'s actual server-side behavior — see the Subtasks bullet above; this dialog *reports* that outcome, it doesn't offer a cascade option that doesn't exist). Fixes C9; C1 (the orphaning bug itself) was already fixed separately. Each row also has a checkbox (leftmost column); a header checkbox selects/deselects every currently-*visible* row — top-level plus any expanded parent's children, not every task that exists — and shows Radix's `indeterminate` state when only some of them are selected. Selecting one or more tasks surfaces a bar above the table ("N selected" / Delete selected / Clear selection); confirming calls `POST /api/tasks/bulk-delete` (`onBulkDelete` prop, `useTasks().bulkRemove`) — the single-task trash icon goes through the exact same call with a one-element array, so there's only one delete codepath in the frontend.
- **To-Do** (`frontend/src/views/TodoView.tsx`) — simplified list, sortable by priority or due date. The checkbox toggles status between `done` and `todo`. Renders the full unfiltered task list handed to it (no subtask filtering — the one view where subtasks show up unconditionally), aside from completed-task hiding, which is shared with every other view (see below).
- **Calendar** (`frontend/src/views/CalendarView.tsx`) — FullCalendar (`@fullcalendar/react` + `daygrid`, pinned to **v6.1.21 across all three `@fullcalendar/*` packages** — `daygrid` has no stable v7 yet, mixing majors breaks the TS types), month view. Tasks place on their start–due range (or a single day, whichever date they have); tasks with neither date aren't shown. Events are colored by priority (`PRIORITY_BG_COLOR`/`PRIORITY_TEXT_COLOR` in `task-display.ts` — real CSS color strings, e.g. `var(--color-primary)`, not Tailwind classes, since that's what FullCalendar's `backgroundColor`/`textColor` event props need). Themed via `src/styles/calendar.css` overriding FullCalendar's CSS with our `--color-*` tokens.
  - **Timezone bug, fixed (C4)**: `toEvents`'s `addDays` used to build the exclusive `end` date for FullCalendar by doing `new Date(iso)` — parsed as *local* midnight since the API's datetime strings carry no timezone marker — then `.toISOString().slice(0, 10)`, which converts back to *UTC*. For anyone ahead of UTC (confirmed with a simulated Europe/Paris, UTC+2, browser timezone via Playwright), that round-trip silently lost a day: a task due 2026-09-30 got an `end` of `"2026-09-30"` instead of `"2026-10-01"`, so with FullCalendar's end being exclusive, the due date's own day never rendered at all (measured directly: the event bar spanned 2 days instead of 3 for a 3-day task). Fixed by parsing as local midnight and formatting back with local getters (`getFullYear`/`getMonth`/`getDate`), never `toISOString()` — same trick `parseDate` already used correctly in `GanttView.tsx`. `start` is now also fed to FullCalendar as a bare `YYYY-MM-DD` (`.slice(0, 10)`) rather than the full datetime string, removing FullCalendar's own date-time parsing as a second place the same class of bug could hide.
- **Timeline** (`frontend/src/views/GanttView.tsx`, still the "Gantt" tab) — hand-rolled with CSS Grid, no external Gantt library. Two were tried and dropped: `gantt-task-react` (hashed CSS-module classnames, couldn't be themed) and `frappe-gantt` (its internal SVG-width-measurement logic never produced a working horizontal scrollbar in this app's layout).
  - **Deliberately not a strict Gantt.** The strict reading is what made it useless: it plotted only *top-level* tasks that *already had dates*, and on the real backlog that was **3 rows out of 40** (37 tasks were subtasks, and none of them had a date). Three rules were relaxed, all on purpose:
    1. **Subtasks get rows**, indented under their parent. This is the one place the "Calendar and Gantt never show subtasks" rule in the Subtasks bullet above no longer applies — Calendar still filters them out, this view doesn't.
    2. **A parent with no dates of its own is drawn as a thin rollup bar** spanning its dated children (`kind: 'rollup'`), visually distinct from a real scheduled bar and not draggable, since there are no own dates to move.
    3. **Undated tasks are not silently dropped.** They sit in a tray under the chart and are dragged onto it to be scheduled — the old version reduced them to a "N tasks without a date not shown" footnote, which on this data meant hiding almost everything.
  - **Drag to schedule/reschedule** (the timeline half of F7): drag a tray pill onto a day (sets start = due = that day), drag a bar to move it (span preserved), drag either edge to resize. All three are pointer-event gestures whose `pointermove`/`pointerup` listeners are registered on `window` per gesture and torn down by the `pointerup` that ends it, so the pointer can leave the bar mid-drag without the gesture dying. `draggedRef` suppresses the click that ends a drag, so dragging never also opens the detail dialog. Releasing anywhere but over the chart cancels rather than committing a silent edit.
  - Rows are built in two passes: parents with their scheduled children, then any scheduled child whose parent isn't on the chart at all (a done/hidden parent) promoted to its own row. **A collapsed parent's children must still be marked seen in that first pass** — without it the promotion pass immediately re-added them as top-level rows and collapsing appeared to do nothing.
  - Bars are always positioned at day granularity (accurate at any zoom); Day/Week/Month zoom only changes how the header and divider lines are *grouped* (`buildGroups`), so it doesn't turn into illegible 4px-wide day cells when zoomed out. Column dividers and weekend shading are **one background layer spanning every row**, not a cell per group per row — the old version rendered rows × groups divs, thousands of them once subtasks were included.
  - The chart is its own scroll container on **both** axes (`max-h-[65vh] overflow-auto`), so the date header stays put vertically (`sticky top-0`) and the task-name column horizontally (`sticky left-0`). The month band's label is itself `sticky` so the month you're looking at stays named while you scroll through it — and the clipping for it lives on the inner `span` (`max-w-full truncate`), not on the cell, because **an ancestor with `overflow-hidden` cancels a descendant's `sticky` outright**. (Same family of trap as the nested-sticky pattern that broke frappe-gantt's header.)
  - `App.tsx`'s `<main>` needs `min-w-0`. As a flex item it defaults to `min-width: auto`, which let the wide timeline grid stretch it past the viewport — so the chart's own `overflow-auto` never got to clip, and the whole *page* scrolled sideways with the toolbar cut off. Affects any wide child, not just this view.
  - The old `onWheel` → `scrollLeft` remap was **removed**: it existed because the chart had no vertical overflow, which stopped being true once every subtask could have a row — hijacking the wheel would have broken scrolling down the list. Horizontal movement is the scrollbar, shift+wheel, or trackpad deltaX.
  - A "Today" button scrolls the chart itself (not the page) to center on today; the chart also auto-centers on today on first layout and on zoom change, but deliberately **not** after a date edit, which would yank the viewport back to today after every drag.
  - No dependency arrows yet.
  - Dates from the API are full datetimes (`"2026-09-30T00:00:00"`), not bare dates — `parseDate` takes `iso.slice(0, 10)` before parsing; forgetting that once already produced silent `Invalid Date`s and a blank chart. Dates are written back with `formatISODate`, which uses local getters and never `toISOString()` (the C4 trap).

Shared display helpers (priority/status labels, badge variants, date formatting) live in `frontend/src/lib/task-display.ts` — use these rather than re-deriving labels/colors per view.

- **Task detail summary**: clicking a task anywhere — a Table row, a To-Do item, a Calendar event, a Gantt bar/label — opens `components/task-detail-dialog.tsx`, a read-only popup surfacing the description (never shown elsewhere; Table/Gantt truncate to one line and To-Do/Calendar don't show it at all) alongside status/priority badges, dates, duration, depends-on/parent context, and tags — deliberately not every field (no timestamps), since this is a quick look, not the edit form. Controlled (`task`/`open`/`onOpenChange` props), not trigger-wrapped like `TaskFormDialog`, since each view's "trigger" is a different kind of element rather than one button to wrap; each view keeps its own `detailTask` state and renders one dialog instance. Table/To-Do had to add `stopPropagation` to their existing per-row interactive elements (expand chevron, status-cycle badge, edit/delete buttons, the checkbox) so clicking those still does only their own thing instead of also opening the summary.
- **Completed tasks**: hidden by default in every view (`status === 'done'`), each view remembering its own "show completed" preference independently — `hooks/use-show-completed.ts` (`useShowCompleted(view)`, `view` a namespacing key: `"table"`/`"todo"`/`"calendar"`/`"gantt"`) persists it to `localStorage` under `planned:showCompleted:{view}`, wrapped in try/catch since storage can throw or be unavailable. The control itself is `components/show-completed-toggle.tsx`, rendered the same way in all four views for a recognizable affordance even though the state isn't shared. Filtering happens client-side on the already-fetched list, not via an API query param. To-Do is the one view with pre-existing "done" handling (sink-to-bottom + strikethrough) — that only kicks in once the toggle reveals them; hidden is still the default there too. Table filters both the top-level list and each parent's children, so a done subtask doesn't linger under an expanded parent. Every view falls back to an explanatory message (not a silent empty state) when its *only* content is hidden-because-done, since an unexplained empty Table/Calendar/Gantt looks broken rather than filtered. Once visible, a done task/subtask/event/bar gets a slightly-green background in all four views (`--done`/`--done-foreground` tokens in `index.css`, same low-chroma treatment as the rest of the warm palette just shifted to a green hue) — `bg-done`/`bg-done-foreground` Tailwind classes in Table/To-Do/Gantt, and `DONE_BG_COLOR`/`DONE_TEXT_COLOR` (real CSS color strings) from `task-display.ts` in Calendar, overriding the priority color the same way `PRIORITY_BG_COLOR` normally sets it.
- **Table sorting**: a "Sort by" dropdown (Default/Priority/Start date/Due date/Status) next to "Show completed" — `sortTasks()` in `TableView.tsx`, applied identically to the top-level list and to each parent's children so an expanded subtask list follows the same order rather than staying in raw insertion order. Priority sorts most-urgent-first (`PRIORITY_WEIGHT`, shared with To-Do's own sort); dates sort earliest-first with undated tasks last; status sorts in workflow order (todo → in_progress → done), a separate `STATUS_WEIGHT` from `PRIORITY_WEIGHT` since status isn't a scale of urgency.
- **Table search & filters**: a search input (matches title or description, case-insensitive) plus Status/Priority/Tag dropdowns, in a row below the main toolbar — `search`/`statusFilter`/`priorityFilter`/`tagFilter` state in `TableView.tsx`, applied (like sorting) to both the top-level list and each parent's children. The tag dropdown is populated from the distinct tags actually in use (`Array.from(new Set(tasks.flatMap(t => t.tags)))`) and only renders at all once at least one task has a tag. Filtering to status "Done" deliberately bypasses the "Show completed" default rather than silently showing nothing — an explicit filter is a more deliberate signal than the toggle's default (`showDone = showCompleted || statusFilter === 'done'`). A "Clear filters" link appears once any filter/search is active, and the empty-state message distinguishes "no match for your filters" (with that same clear-filters affordance) from "everything's hidden because it's done".
  - **A matching subtask is reachable even when its parent doesn't match.** Only top-level rows are ever mapped (children render underneath one), so a first version of this filtering made a matching subtask completely invisible — the view showed "1 task" in the counter and "No tasks match your search/filters" in the table *at the same time*, for a real match. With filters active, `rootTasks` therefore also keeps a non-matching parent as a **carrier row** when one of its children matches, and promotes a matching subtask to a standalone row when its parent isn't on screen at all to carry it (a done/hidden parent). `isRowExpanded` auto-reveals matching children while a filter is on, so the match isn't left behind a chevron — the trade-off being that collapsing is inert until the filter is cleared. With filters off, the row list is byte-for-byte what it always was.
- **Light/dark theme**: `hooks/use-theme.ts` + `components/theme-toggle.tsx`, one icon button in `App.tsx`'s top nav cycling **System → Light → Dark**. The state/presentation split is the same as `useShowCompleted`/`ShowCompletedToggle` (hook called in `App.tsx`, component is presentational), but unlike that one the preference is global, not per-view — `localStorage` key `planned:theme`, same try/catch since storage can throw.
  - `"system"` is the default and *keeps* following the OS: a `matchMedia('(prefers-color-scheme: dark)')` `change` listener re-resolves live, so a desktop switching to dark at sunset carries over without a reload. `"light"`/`"dark"` pin it.
  - Applied by toggling the `dark` class on `<html>` — that's what `index.css`'s pre-existing `@custom-variant dark (&:is(.dark *))` and its `.dark` token block key off. **The whole dark palette already existed in `index.css`; nothing but the activation mechanism was missing.** Because every color in the app resolves through a `--color-*` token (including `task-display.ts`'s real CSS color strings, which are `var(--color-…)` references, and `styles/calendar.css`'s FullCalendar overrides), no view needed per-component dark styling.
  - `index.html` carries a small inline script that resolves and applies the same rule **before first paint**, so the app never flashes light before React mounts. It duplicates the storage key and the no-preference-means-follow-the-OS fallback out of necessity (it runs before the bundle) — keep the two in sync.
  - `:root`/`.dark` also set `color-scheme: light`/`dark` so the browser's own chrome (scrollbars, native form controls) follows; without it a dark page keeps light scrollbars.
  - **The light palette was re-tuned in the same pass** (`:root` in `index.css`), because putting the two side by side showed the light side was the washed-out sibling: surface chroma sat at 0.006-0.025 against dark's 0.018-0.026, so it read as plain white rather than warm, and `--background`/`--card` were only 0.010 apart in lightness against dark's 0.040, so the nav, the content area and the chat sidebar all melted into one flat sheet. Both themes now follow the same two rules, written at the top of the palette block: **surface chroma in the 0.010-0.034 band, and a visible background↔card lightness gap** (~0.02 light, ~0.04 dark). Re-checked every text/background pair for WCAG AA afterwards by rasterizing each token through a canvas — `getComputedStyle` hands back the `oklch()` string untouched, so reading its three numbers as RGB silently reports ~1.0 for everything. Lowest surviving pair is `muted-foreground` on `muted` at 5.44 (light) / 4.82 (dark); the rest clear AAA.
  - Two off-palette leaks fixed along the way, both pre-existing and both invisible until dark mode made them obvious: the Radix dialog scrim was a flat `bg-black/10` (near-invisible over a dark background — now `dark:bg-black/50`), and FullCalendar's `.fc .fc-button-primary:disabled` outspecifies `calendar.css`'s `.fc .fc-button` rule, so the "today" button kept FullCalendar's default navy `#2C3E50` in *both* themes. Verified with Playwright that only palette tokens are painted afterwards.
- **Backup**: `components/backup-controls.tsx`, rendered in `App.tsx`'s top nav (global, not per-view) — Export downloads the current task list as `planned-backup-<date>.json` (`lib/backup.ts::downloadTasksBackup`, client-side `Blob` + a synthetic `<a download>` click, no backend endpoint needed since `GET /api/tasks/` already returns everything); Import reads a JSON file and creates tasks from it in two passes, the same shape as `ChatPanel`'s `parentRef` handling: pass 1 creates every row flat (no `parentId`/`dependsOn` yet) via the plain `createTask` calls (not `useTasks().add`, to avoid a full-list refetch per row), collecting old id (from the file) → new id; pass 2 `PATCH`es `parentId`/`dependsOn` back in now that every target exists, dropping a reference to an id that wasn't in the file rather than failing the batch. A `window.confirm` (matching the existing Quit-button idiom) gates the import since it's additive but still bulk-creates; a single `refresh()` runs once at the end.
  - **Per-row resilience, not all-or-nothing**: each row's `createTask`/relink `updateTask` call is individually try/caught rather than the whole two-pass loop being wrapped in one try/catch — a real incident is why: an import ran while the backend happened to restart mid-batch (unrelated dev-server work), the first failing request threw out of the *original* single outer try/catch, and every row created before that point was left behind permanently as a flat, unlinked duplicate — 35 of them, silently, with the UI just showing a generic "failed" message. Now a failed row is recorded (`failedCreates`/`failedRelinks`, both title lists) and the loop moves on; the status message reports `Imported X/N tasks` plus which ones couldn't be created or linked, so a partial failure is visible and actionable instead of silently corrupting the list. Restoring after that incident: `POST /api/tasks/bulk-delete` (added the same day, see below) with the exact stray ids, identified by every duplicate sharing one import's `created_at` timestamp *and* an already-existing title.
  - Addresses F2's "no way to get data out" half; the other half — an unattended single SQLite file with no backup — is `db.py::_backup_db`, which copies `~/.planned/planned.db` to `~/.planned/backups/planned-<UTC timestamp>.db` once per backend startup (before `create_all()`/migrations touch it), pruning to the last `BACKUP_RETENTION` (10) copies. No scheduler, since this is a locally-run single-user app restarted reasonably often (`scripts/start-planned.bat`).

`App.tsx` owns the single `useTasks()` call (`frontend/src/hooks/use-tasks.ts`) and passes `tasks`/`loading`/`error` plus the `add`/`edit`/`bulkRemove`/`refresh` callbacks down as props — views themselves don't fetch. `ChatPanel` gets `tasks` too (it needs the live values to diff a proposed update against) plus `edit` as `onUpdateTask`; `BackupControls` gets `refresh` as `onImported`. `use-tasks` refetches the full list after every mutation rather than updating state optimistically; fine while the list is small and local. There is deliberately **no single-task delete** in the frontend — `bulkRemove` covers both, the Table's per-row trash icon just passing `[task.id]`, so there's one delete codepath to reason about (`DELETE /api/tasks/{id}` still exists and is tested server-side, it simply has no frontend caller).

### Backend

- `main.py` — FastAPI app, CORS for the Vite dev server (`http://localhost:5173`), mounts routers, runs `init_db()` on startup.
- `db.py` — SQLite engine; DB file lives at `~/.planned/planned.db` (outside the repo). Dev DB, not seeded — delete the file to reset. `init_db()` runs `_backup_db()` (see the Backup bullet above) then `_run_column_migrations()`, a tiny startup migration — `create_all()` alone only creates missing tables, not missing/removed columns on ones that already exist. `_COLUMN_MIGRATIONS` (checks `PRAGMA table_info`, runs `ALTER TABLE ... ADD COLUMN` for anything missing) needs a new tuple whenever a field is *added* to an existing model; `_COLUMN_DROPS` (`ALTER TABLE ... DROP COLUMN`, SQLite ≥3.35) is the symmetric case for a field *removed* — skipping this isn't optional: when `progress` was dropped from `Task`, every existing DB's `task.progress` column was still `NOT NULL` with no default, so every `INSERT` 500'd (`sqlalchemy.exc.IntegrityError: NOT NULL constraint failed`) until the drop migration ran, even though a *brand-new* DB (created fresh from the already-updated model) was unaffected — the bug only showed up against a database that pre-dated the field removal, and `backend/tests/test_tasks.py`'s `client` fixture creates its schema straight from the current model rather than through `init_db()`'s migration path, so pytest passing proved nothing about this. Caught by exercising the real dev server, not by the test suite.
- `api/tasks.py` — task CRUD: `GET /api/tasks/`, `POST /api/tasks/` (body: `TaskCreate`), `PATCH /api/tasks/{id}` (body: `TaskUpdate`, partial), `DELETE /api/tasks/{id}`, `POST /api/tasks/bulk-delete` (body: `{"ids": [...]}`, response: `{"deleted": [...]}` — only the ids that actually existed; an unknown id is dropped rather than failing the whole request). `TaskCreate`/`TaskUpdate` (in `models.py`) exclude server-owned fields (`id`, `created_at`, `updated_at`). Single and bulk delete share `_detach_references(session, ids, keep_ids)` for the orphan-promotion/depends_on-clearing logic (see the Subtasks bullet above) — `keep_ids` is the set of ids also being deleted in the same call, so e.g. bulk-deleting a parent and its child together doesn't try to "promote" a child that's being deleted anyway.
- `api/chat.py` — `POST /api/chat/`: prepends a system prompt (today's date + a summary of the user's current open tasks, so the model can schedule around existing deadlines/workload) and offers the model two tools, `propose_tasks` (new tasks) and `propose_task_updates` (F5 — changes to existing ones). Forwards the full message history to `llm/client.py::LocalLLMClient`. Stateless — the client resends the whole conversation every time. Wraps LLM errors as `HTTPException` with a message meant to be shown as-is to the user: **503** when the server can't be reached at all (LM Studio/Ollama not running), **504** on `openai.APITimeoutError` — kept distinct because "is LM Studio running?" sends you looking in the wrong place when it *is* running and merely slow.
  - This endpoint **never writes to the database**. When the model calls a tool, the response carries `proposed_tasks` or `proposed_updates` (unpersisted) instead of just `content`; the frontend shows them for the user to confirm, and only then applies them via the normal `POST`/`PATCH /api/tasks/` endpoints (reusing `useTasks().add`/`.edit`) — this "propose, never write, confirm before anything happens" shape is the *whole* mitigation for S2 (prompt-injection risk via task content in the summary, still open) discussed below; it's why F5 could be built without S2 landing first.
  - **F5 — reschedule/complete/edit an existing task from chat**: `propose_task_updates` takes an array of `{task_id, ...only the fields that are changing}` — `_existing_tasks_summary` now prefixes every open task with `[id N]` so the model has real ids to reference (it didn't before F5; nothing needed them). `_build_proposed_updates` (plain function, unit-tested in `test_chat.py` without needing a running LLM) drops any update whose `task_id` isn't in the *currently open* set queried for this same request — a hallucinated, already-done, or already-deleted id is silently dropped rather than trusted, since these ids come from the model referencing free-form context rather than an index it fully controls (contrast `parent_ref` below, which is bounds-checked against a batch the model itself just generated). Every field it does keep must also pass a per-field coercer (`_UPDATE_FIELDS`) — see the coercion bullet below. Only the keys the model actually included survive into the response (`ChatResponse.proposed_updates: list[dict]`, deliberately a loose dict rather than a fixed-field Pydantic model, so a field's total absence — "leave it alone" — can't collapse into an explicit `null` — "clear it" — the way a model with defaulted fields would force). The prompt tells the model: reference an existing task only by its `[id N]`, and if it can't confidently tell which task a partial/ambiguous title means, ask a clarifying question in plain text instead of guessing an id (tested: two tasks both starting "Rediger le rapport…" — asked which one rather than picking either). `ChatPanel` renders each proposed update as a title + one "`field: before → after`" line per changed field (`diffLines`, reading the *current* live value of that field so the diff is real, not just the new value shown alone), with Apply/Discard like creates; Apply calls the `onUpdateTask` prop (`App.tsx` passes `useTasks().edit`) once per update, skipping (not erroring on) any target that's been deleted since the reply was generated.
  - The tool schema requires absolute `YYYY-MM-DD` dates — without an explicit instruction + today's date in the prompt, the model (tested: Gemma via LM Studio) outputs relative phrases like `"next Friday"` instead.
  - **Task quality from chat, tested and prompt-tuned**: the goal is that pasting a raw request (a one-liner, a forwarded email) produces a task with a real `description` and a workload estimate, not just a title. Baseline testing — 6 varied prompts run against LM Studio (a scoped feature, a personal chore, a noisy pasted email, an explicit multi-step project, a big vague technical ask, a one-line bug report) — showed the model leaving `description` empty and `duration_hours` null on every single proposed task (16/16), and drifting into inconsistent tag casing (`"Client Feature"`, `"UI/UX"`) instead of matching the app's own lowercase style. Two further edge cases surfaced real bugs, not just gaps: a wrong weekday computation (`"vendredi"` → Saturday) and an outright refusal on a legitimate but trivial/personal ask (`"acheter du pain"`), apparently anchored on the software-heavy existing-task examples shown in context. Fixed by rewriting `_build_system_prompt`: it now spells out what `description`/`duration_hours`/`priority`/`tags` each mean and require, states today's weekday name explicitly (not just the ISO date) and asks the model to double-check relative-date arithmetic, states plainly that Planned tracks any kind of task and a short/mundane one should never be refused, and calls out de-escalating cues (`"pas urgent"`) as well as urgency ones so priority isn't a one-way ratchet. `_existing_tasks_summary` also now surfaces the distinct tags already in use as a style reference. Re-tested after the change: description and duration_hours filled on every task across the same 6 prompts (plus the two edge cases), tags matching existing style, correct weekday math, no more refusals. Some non-determinism remains run-to-run (a locally-hosted, quantized small model) — e.g. whether subtasks each get their own duration/description varies — which prompt wording alone won't fully remove.
  - **Field coercion at the tool-call boundary** — the model's tool-call arguments are the one place in this app where free-form model output becomes an API payload, so anything a later `POST`/`PATCH` would reject is caught in `chat.py` rather than surfacing to the user as a raw 422 about a request they never knowingly made. One shared set of coercers (`_coerce_text`/`_coerce_date`/`_coerce_number`/`_coerce_tags`/`_coerce_priority`/`_coerce_status`) backs both tools, each returning `(usable, normalized)`; what "unusable" *means* differs by caller, and that difference is load-bearing:
    - `propose_tasks` falls back to the field's default (`ProposedTask`'s `field_validator(mode="before")` hooks), so one bad field costs that field, not the task. A prose `duration_hours` ("about 3 hours") used to raise `ValidationError` and silently discard the whole proposal, title and description with it.
    - `propose_task_updates` omits the key entirely, because there an explicit `null` is a real "clear this field" instruction — falling back to a default would *become* an edit.
    - Caught this way, each verified against the real endpoint: a relative date (`"next Friday"` — the prompt argues against these precisely because the model still reaches for them) and an impossible one (`2026-13-45`); a priority outside the enum (`propose_tasks` had no enum guard at all, only updates did); `tags: null`, which is worse than a 422 — `ChatPanel`'s `diffLines` does `u.tags.join(', ')`, so it threw while *rendering* and took the chat panel down with it; and `title: null`, which would have reached `setattr` in the `PATCH` handler and blanked the stored title, since `TaskUpdate.title` is `Optional[str]`. A full datetime is narrowed to its date part rather than dropped.
  - A malformed tool call (seen live: the model omitting `title` on one task in an otherwise-valid batch) used to crash the whole request with a 500. `_validated_tasks` drops just that task — same "degrade, don't reject the batch" spirit as `_sanitize_parent_refs` below — falling back to plain `content` (asking the user to rephrase) only if every task in the batch was malformed.
  - **Subtasks from chat**: each proposed task carries an optional `parent_ref` — a 0-based index into the *same* `tasks` array (not a real id, since none exist yet), letting the model propose a top-level task plus its subtasks in one call instead of only ever flat/unrelated tasks. `_sanitize_parent_refs` drops any ref that's out of range, self-referential, or points at another subtask (keeps the one-level-deep rule from `api/tasks.py`), so a malformed ref degrades to "just create it top-level" rather than corrupting the batch. **`_validated_tasks` must remap every `parent_ref` before that check runs**, because dropping an untitled task renumbers the very array the refs index into: `[invalid, "Design", "Build", subtask(parent_ref=1)]` left the subtask attached to `"Build"` instead of `"Design"` — nothing errored, the batch was just silently wrong, and the trigger (a task missing its title) is a case already seen live. A ref whose parent was itself dropped resolves to `None`, leaving that child top-level. `_existing_tasks_summary` also now shows each open task's parent, if any, in the context. The model doesn't reliably choose to structure a multi-step request this way on its own (tested: it happily proposed 3 unrelated top-level tasks for a "design → dev → launch" request) but does use `parent_ref` correctly when the user is explicit ("create X with subtasks Y and Z") — that's a prompting/model-capability gap, not a mechanism bug; the mechanism itself is confirmed working end-to-end.
  - Frontend side: `ChatPanel.handleCreateProposed` creates in two passes — every `parentRef === null` task first (collecting real id per array index), then every subtask, resolving its real `parentId` from that map. `toDraft()` builds a clean `TaskDraft` from a `ProposedTask` (deliberately not spread — `ProposedTask` carries `parentRef`, which isn't a `TaskDraft` field).
- `api/system.py` — `POST /api/system/shutdown`: kills the frontend dev server by port, then this process (Windows-only, local-dev-tool-only — do not expose this beyond localhost). Backing the in-app "Quit app" button. Any subprocess call that shells out to `netstat`/`taskkill` here must decode output as `latin-1`, not `text=True`'s locale-guessed default — `netstat`'s console output isn't reliably valid cp1252 (seen: a silent `UnicodeDecodeError` in a subprocess reader thread on French Windows, which an `except OSError` didn't even catch since it surfaces as `AttributeError` on the caller side).
- `llm/client.py` — thin wrapper around the `openai` SDK pointed at a local base URL (LM Studio: `http://localhost:1234/v1`, Ollama: `http://localhost:11434/v1`); works for either since both expose an OpenAI-compatible chat-completions API. The model name (`config.py::LLM_MODEL`, `"local-model"`) is a placeholder — LM Studio ignores it and serves whatever model is currently loaded, confirmed working; Ollama needs a real model name if you switch to it. `chat()` optionally takes an OpenAI-style `tools` list and surfaces the first tool call (if any) alongside the text content — confirmed working against LM Studio's default model (Gemma). **`timeout`/`max_retries` are set explicitly** (`config.py::LLM_TIMEOUT_SECONDS` = 120, `LLM_MAX_RETRIES` = 1): the SDK defaults are a 600s read timeout and 2 retries, which let a wedged local server hold one request for ~30 minutes with the chat panel stuck on "Thinking…". The frontend pairs this with a Stop button — `use-chat.ts` holds an `AbortController` and `cancel()` aborts the in-flight fetch, treated as a deliberate action rather than an error (the user's own message stays in the history so it can be resent without retyping).
- Dev venv lives at `backend/.venv` (gitignored); use `./.venv/Scripts/python.exe` (Windows) to run commands inside it without activating.
- `uvicorn --reload` has, more than once in this environment, logged `WatchFiles detected changes ... Reloading` and then kept serving the *old* code for the next request or two — a real behavior seen while testing, not a one-off fluke. Don't trust "it reloaded" from the log alone when verifying a fix; if a request doesn't behave as the new code should, stop the process and start it fresh before concluding the code is wrong.

### Frontend

- `App.tsx` — owns the active-view state, the shared task data (via `useTasks`), and the top nav; add new views here.
- `lib/api.ts` — fetch wrapper for the task API (the only place that knows about the backend's snake_case JSON shape), plus `sendChatMessage` and `shutdownApp`.
- `views/ChatPanel.tsx` + `hooks/use-chat.ts` — the sidebar chat. Conversation lives only in React state (not persisted, resets on reload); `use-chat` resends the full history on every message since the backend is stateless. When a reply carries `proposedTasks`, `ChatPanel` renders a preview card (per message, tracked by array index in `resolvedProposals`, subtasks shown indented/smaller like Table's rows) with Create/Discard — Create calls the `onCreateTask` prop (App.tsx passes `useTasks().add`) in two passes to resolve `parentRef` into a real `parentId` (see `api/chat.py`'s subtasks note above). A reply carrying `proposedUpdates` (F5) instead renders each as a title + before/after diff lines, with Apply/Discard — see `api/chat.py`'s F5 bullet above for the full shape.
- shadcn/ui is configured for Tailwind v4 (`components.json`, no `tailwind.config.ts` — theme tokens live in `src/index.css` via `@theme inline`). Add components with `npx shadcn@latest add <name>` from `frontend/`.
- Path alias `@/*` → `frontend/src/*` (configured in both `tsconfig.json` and `vite.config.ts`).
- `vite.config.ts` proxies `/api` to `http://localhost:8000` — run the backend on port 8000 for the frontend dev server to reach it.

## Commands

### Backend (run from `backend/`)

```
pip install -e .[dev]              # install with dev extras (pytest, httpx)
uvicorn planned.main:app --reload  # run the API on http://localhost:8000
pytest                             # run all tests
pytest tests/test_health.py::test_health  # run a single test
```

### Frontend (run from `frontend/`)

```
npm install
npm run dev       # Vite dev server, http://localhost:5173
npm run build     # tsc -b && vite build
npm run preview   # preview the production build
```

There is no lint tooling configured yet (the `lint` script in `package.json` references `eslint`, which isn't installed).

Run both servers to use the app: the backend on port 8000, the frontend dev server on 5173 (proxies `/api` to the backend).

### Daily use (Windows)

`scripts/start-planned.bat` starts both servers (each in its own window — close a window or Ctrl+C in it to stop that server) and opens the app in the browser. It force-frees ports 5173/8000 first, so it's safe to double-click again even if a previous run is still hanging around. A desktop shortcut ("Planned") points to it. Assumes `backend/.venv` and `frontend/node_modules` already exist (first-time setup still needs the manual install commands above). Runs the backend **without** `--reload` (single process — the in-app "Quit app" button relies on there being exactly one backend process to kill by port; use the `--reload` command above instead when actively developing). The "Quit app" button (in `ChatPanel.tsx`) calls `POST /api/system/shutdown` to stop both servers without touching either console window.
